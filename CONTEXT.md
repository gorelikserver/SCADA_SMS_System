# SCADA SMS System — Codebase Context

## Purpose

This repository contains a Windows-oriented SCADA SMS notification system. WinCC OA or another SCADA client posts an alarm message and target group to the application; the application resolves eligible group members, sends one SMS per recipient through a configurable REST or SOAP provider, and records delivery attempts for auditing. It also provides a Razor Pages administration UI for users, groups, alarm mappings, holidays, provider settings, testing, and audit history.

## Technology and deployment

- .NET 9 ASP.NET Core web application (`SCADASMSSystem.Web.csproj`)
- Razor Pages UI plus attribute-routed API controllers
- Entity Framework Core 9 with SQL Server, SQL Express, or LocalDB
- Serilog console and rolling-file logging
- Bootstrap 5 and jQuery in the browser
- Hosted background service for queued SMS delivery
- Optional Windows Service hosting
- WiX v4 installer and self-contained `win-x64` release tooling
- Playwright end-to-end tests (currently focused on SOAP/configuration behavior)

The solution has one main web project and a separate WiX installer project under `Installer/`.

## Runtime architecture

The main delivery path is:

1. SCADA invokes `Scada_sms.bat` or calls `POST /api/sms/send`.
2. `Controllers/SmsController.cs` validates the payload and calls `SmsBackgroundService.QueueSmsMessageAsync`.
3. `Services/SmsBackgroundService.cs` places the request in an in-memory `ConcurrentQueue` and processes it in a hosted background loop.
4. `Services/SmsService.cs` loads eligible recipients through `IUserService`, applies rate limiting and duplicate suppression, resolves dynamic provider parameters, and sends REST or SOAP requests (or uses the in-process mock in test mode).
5. Each per-recipient attempt is written to the SMS audit data through `IAuditService`.

The accepted SCADA payload is:

```json
{
  "message": "Equipment failure detected",
  "groupId": 1,
  "value": "85.3 PSI",
  "alarmId": "ALM-2024-0142",
  "priority": "urgent"
}
```

`message` and a positive `groupId` are required. `priority`, when supplied, is `normal`, `urgent`, or `critical`. `value` and `alarmId` are optional. Compatibility routes also accept `POST /api/sms/queue`, `POST /api/sms`, and root-level `POST /`. Status endpoints include `/api/sms/status`, `/api/sms/health`, root `/status`, and the ASP.NET health endpoint `/health`.

The in-memory queue now serves only the legacy asynchronous endpoints and is not durable. Critical alarms from `Scada_sms.bat` bypass it: they are delivered synchronously, tracked per recipient in SQL and backed by the spool folder (see below).

## Critical integration entry point: `Scada_sms.bat`

`Scada_sms.bat` is the only channel from the Akara SCADA system into this application. Treat its contract as ground truth.

### Fixed constraints

- The Akara alarm-action command template cannot be changed. Akara always calls the batch file with exactly three arguments: `DESCRIPTION`, the group ID and `ALM_VALUE`. The template is generated by `AlarmActionService.BuildSmsCommandForGroupId` and must stay byte-for-byte identical.
- Akara is fire-and-forget. It ignores the exit code and never retries. All reliability (spooling, retries, failure visibility) belongs to this application.
- Sites are air-gapped. The batch file uses only `cmd.exe`, built-in Windows PowerShell and curl (bundled `..\Tools\curl.exe`, else `curl.exe` on `PATH`).

### Invocation contract

```bat
Scada_sms.bat MESSAGE GROUP_ID [VALUE] [ALARM_ID] [PRIORITY]
```

| Position | JSON field | Behavior |
| --- | --- | --- |
| `%1` | `Message` | Required alarm text |
| `%2` | `GroupId` | Required; digits only |
| `%3` | `Value` | Optional measurement value; omitted from JSON when empty |
| `%4` | `AlarmId` | Optional, manual/testing only; when empty the batch generates `SCADA-<guid>` |
| `%5` | `Priority` | Optional; defaults to `normal` |

### Flow

1. Validate arguments (exit `1` on missing message/group or non-numeric group).
2. Read optional `Scada_sms.ini` next to the batch file (`URL=`, `SPOOL_ROOT=`, `MAXTIME=`, `CURL=` full path of curl.exe). Defaults: `http://localhost:5000/api/sms/send`, `%ProgramData%\SCADA_SMS`, `120` seconds.
3. One PowerShell call picks the AlarmId, serializes the JSON (Unicode, quotes and backslashes handled by `ConvertTo-Json`, values passed through environment variables) and writes it atomically (`.tmp` then rename) to `<SPOOL_ROOT>\spool\<AlarmId>.json`, including `ReceivedAt` (UTC).
4. POST the spool file to the service with curl and wait. The service answers only after every provider call finished: `200` when every eligible recipient was accepted, `502` when any recipient failed or the group has no eligible recipients.
5. Delete the spool file only on HTTP `200`. In every other case it stays for the service to retry.
6. Append one line per call to `<SPOOL_ROOT>\Scada_sms.log` (time, AlarmId, group, HTTP status, curl code, exit code). Akara keeps no record, so this log is the proof an alarm reached us.

Exit codes: `0` all accepted, `1` bad arguments or spool write failed, `2` service unreachable or timed out, `3` delivery failed or partial, `4` rejected by the service.

The file must stay **pure ASCII without a BOM, with CRLF line endings**. Under the default OEM code page `cmd.exe` runs a BOM as part of the first command, so `@echo off` fails and every command is echoed. Hebrew alarm text is unaffected: arguments arrive as Unicode and reach PowerShell through environment variables.

### Service side

- `SmsController` `/api/sms/send` calls `ISmsService.SendCriticalSmsToGroupAsync` synchronously. Each recipient is claimed in `scada_critical_sms_deliveries` with a unique `(AlarmId, PhoneNumber)` key. Re-sending the same AlarmId skips recipients already accepted and re-sends `FAILED`, `INDETERMINATE` (timeout or transport loss) and `SENDING` rows older than 5 minutes (crashed request). A duplicate SMS is preferred over a missed alarm. Within one request, status 0, 429 and 5xx are retried up to `RetryAttempts` times; other 4xx are permanent. Rules live in `CriticalDeliveryPolicy`.
- `SpoolIngestService` (`ScadaSpool` section in `appsettings.json`) scans the spool every `PollSeconds`. Files older than `MinAgeSeconds` (must exceed the batch `MAXTIME`) are re-sent with their original AlarmId. Fully accepted files are deleted; files older than `MaxAgeMinutes` move to `spool\failed` with a critical log entry; malformed files move to `spool\bad`.
- The spool root in `ScadaSpool:Root` and the batch `SPOOL_ROOT` must point to the same folder.

### Packaging

`build.bat` copies the root `Scada_sms.bat` into `deployment_package\Scripts` (and `curl.exe` into `Tools` when available). The MSI (`build-release.ps1` -> `Installer/`) installs the same file byte for byte to `[INSTALLDIR]Scripts\Scada_sms.bat`. It bundles `curl.exe` into `[INSTALLDIR]Tools\` only when the build found one (`-CurlPath`, `temp_curl\curl.exe` or `deployment_package\Tools\curl.exe`); otherwise the bat uses the Windows built-in `curl.exe` (Windows 10 1803+ / Server 2019+). `build-release.ps1` fails if the bat is missing or not pure ASCII.

The MSI creates `%ProgramData%\SCADA_SMS\spool` with a protected, inherited ACL: SYSTEM and Administrators get Full control and BUILTIN\Users get Modify, because the account Akara runs under is unknown. Trade-off: any local user can read, add or delete spool files and the log. `install_service.bat` applies the same ACL. The MSI also registers the `SCADA SMS System` Application event source.

The installer's HTTP port (`APP_PORT`, default 5000) is written as `Urls` (`http://localhost:<port>`) to `appsettings.Production.json` and as `URL=` to `Scada_sms.ini` next to the installed bat, so the service and the bat always agree.

The installer's log folder (`LOG_DIR`, default `C:\SCADA\Logs`, remembered in `HKLM\Software\Afcon\Scada SMS\LogDir`) is written as `Logging:File:Path` (`<LOG_DIR>\scada-sms-.log`). That key drives the only Serilog file sink (`Program.cs`, daily files, 31 kept); `Serilog:WriteTo` must not add another file sink, or every line is logged twice. Logs are outside `%ProgramData%\SCADA_SMS` and survive uninstall.

Uninstall and major upgrades remove the install folder (bat, ini, curl, `appsettings.json`) and uninstall removes the event source, but never anything under `%ProgramData%\SCADA_SMS`: spool files, `Scada_sms.log` and `config\settings.json` (provider profile and UI settings) survive.

**Akara calls the bat from its `PCIMUTIL` alias folder**, not from the install folder. The installer has an optional "Akara PCIMUTIL folder" field (`PCIMUTIL_DIR`, remembered in `HKLM\Software\Afcon\Scada SMS\PcimUtilDir` so upgrades reuse it). When set, the `ConfigureAppSettings` custom action copies `Scada_sms.bat` there on every install and upgrade and writes `Scada_sms.ini` next to it with `URL=` and `CURL=` (the bundled curl in `[INSTALLDIR]Tools`), keeping other lines an engineer added. The copy is deliberately not an MSI-owned file: uninstall and the remove step of a major upgrade leave it in place, so alarms raised while the service is down are still spooled and delivered after reinstall. The folder is passed to the app as `Scada:PcimUtilDir`; `ScadaLinkChecker` compares the copy with `[INSTALLDIR]Scripts\Scada_sms.bat` (SHA-256) and the ini's `URL=` with the service's `Urls`, and a missing, outdated or mis-pointed copy raises a red banner. Without the field, copy `Scada_sms.bat` and `Scada_sms.ini` by hand; the app then shows the link as not checked.

### Validation checklist

- Run in Windows `cmd.exe`, not WSL or PowerShell.
- Cover: service up (200), partial failure (502), service down, non-numeric group, Hebrew text with `&`, `!` and quotes.
- Confirm the spool file is deleted only on 200 and that `Scada_sms.log` records every call.

## Provider profiles (how an SMS is actually sent)

`SmsService` sends every SMS through one data-driven `ProviderProfile` (`SmsSettings:Profile`); there is no provider-specific REST or SOAP code. A new provider at an air-gapped site means a new profile, not a code change.

- **Request:** method, URL template, headers, body template of any content type (JSON, form, XML/SOAP 1.1/1.2, text), variables (constants and secrets), auth (`None`, `Basic`, `Bearer`, `WsSecurity` UsernameToken injected into the envelope header), and a phone format (`AsStored`, `DigitsOnly`, `E164`, `International`, `Local` with a country code).
- **Templates:** `{Name}` or `{Name:raw|json|xml|url|base64}`. Built-ins: `Message`, `Phone`, `Value`, `AlarmId`, `Priority`, `GroupId`, `UserId`, `FirstName`, `LastName`, `TZ`, `Now[:format]`, `Guid`; anything else must be a profile variable. Without a suffix the encoding follows the location (URL, body content type, header). Unknown tokens are errors, never sent.
- **Acceptance:** failure rule first, then success status codes (`2xx`, `200,202`), then the success body rule (`Contains`, `Regex`, `JsonPath` `$.a.b[0]`, `XmlElement` with optional expected value; two matching elements are ambiguous and not accepted). For `Kind: SOAP` a SOAP Fault always fails and a body success rule is required.
- **Validation:** `ProfileValidator` renders a sample alarm (quotes, `&`, `<`, Hebrew) and checks URL, JSON/XML well-formedness, that `{Message}` and `{Phone}` are sent, variable names, auth and rules. An invalid profile blocks sending (status `-1`, not retried in-request) and shows a red banner.
- **Draft, verify, activate** (`Settings > SMS Provider`, `ProviderProfileService`): admins edit a draft (start from a built-in template, import a JSON file, or the active profile), preview the masked request for a sample alarm, then **verify** it with a real SMS to a test phone (always real, even in test mode). Only a draft whose exact SHA-256 matches its last accepted verification can be activated; any edit needs a new verification. Alarms keep using the active profile meanwhile. Exports leave secrets empty so profiles can be carried between air-gapped sites.
- **Cutover:** the pre-profile provider fields no longer exist in `SmsSettings` (only `LegacySmsSettings`, read by the startup cutover). At startup a site without a profile has its old fields, as the app effectively saw them (all settings files and environment variables), converted by `LegacyProfileConverter` into the active profile; the old keys are removed from `appsettings.json` (previous file in `settings-backups`). A fresh install has no profile: alarms are refused and the banner points to the editor.
- **Settings page** edits only general fields (test mode, rate/timeout/retry, PCIM id, SOAP log). **Test SMS** sends a test alarm to a group through the same synchronous path as `Scada_sms.bat` and shows each recipient's result.
- Code: `Models/ProviderProfile.cs`, `Services/Providers/` (template, phone formatter, request builder, response evaluator, validator, converter).

## Settings history and rollback

`Settings > History` (`Pages/Settings/History`, admin only) shows what changed and lets an admin go back to an earlier provider profile.

- **Change history** (`scada_settings_changes`): one row per meaningful change with time, user, area (`General`, `Provider`), action (`GeneralSaved`, `DraftImported`, `DraftStartedFromTemplate`, `DraftVerified`, `DraftDiscarded`, `ProfileActivated`, `ProfileRestoredAsDraft`) and a readable summary. General saves list the changed fields as `old → new` and write nothing when nothing changed. Profile summaries never contain secret values (only "secret X changed"); URL, body, headers and auth templates are reported as "changed" without values. Draft autosaves are not recorded.
- **Profile versions** (`scada_provider_profile_versions`): every activation stores the full profile JSON (secrets included: this table is the rollback source, treat the database as sensitive), its SHA-256 hash, name, kind and who/when activated and verified. The row whose hash matches the active profile is marked active.
- **Pre-existing active profile**: a profile that was active before history existed (converted at startup or activated in an earlier version) gets a version row, with a note, the first time the History page is opened or, at the latest, just before an activation replaces it. Its time is when history first saw it.
- **Rollback is never direct**: "Restore as draft" copies a version into `DraftProfile` and removes any stored verification, so it goes live only after a new real test send and activation in the editor. "Export" uses `ProfileManagement.Export` (secrets empty).
- History writes never fail or block a settings change: `SettingsHistory` logs database errors and continues. Summaries are built by the pure `SettingsChangeSummary` (`Services/SettingsHistory.cs`).

## Failure visibility, access control and secrets

- **Delivery alerts.** `DeliveryAlertService` collects critical alarms that did not reach every recipient (from `scada_critical_sms_deliveries` and the spool folders), unreadable spool files, groups with no eligible recipients right now, and SMS-enabled users with an invalid phone number. The `SystemAlerts` view component shows them as a banner on every page; `/Alerts` lists them and lets a user acknowledge an alarm (`scada_alarm_acknowledgements`, records who). Acknowledging hides the banner; it does not stop retries.
- **Windows Event Log.** `UseSerilog()` replaces the Microsoft logging providers, so `ILogger` never reaches the Event Log. `EventLogAlertNotifier` writes directly (source `SCADA SMS System`, event IDs 1001 incomplete delivery, 1002 spool gave up, 1003 rejected spool file). Creating the source needs admin rights; the service runs as LocalSystem and `install_service.bat` pre-registers it.
- **Accounts.** Local accounts in `scada_accounts` (PasswordHasher, 5 failed logins lock for 5 minutes). `/Account/Setup` creates the first admin and only works while no account exists. Roles: `Admin` (everything) and `Viewer` (dashboard, alerts incl. acknowledge, audit, calendar, help). Admin-only folders are set in `Program.cs`. `Scada_sms.bat` endpoints, the mock provider, `/health` and static files are anonymous.
- **Debug pages** return 404 outside Development.
- **Group delete** is refused while any SCADA alarm action references the group, or when that check fails.
- **Phone numbers** must have 7-15 digits (`PhoneNumberRules`); duplicates compare digits only.
- **Where UI settings live.** Everything edited in the UI (`SmsSettings`: provider profile, draft, verification, limits, test mode) is stored in `%ProgramData%\SCADA_SMS\config\settings.json`, not in the install folder, because an MSI major upgrade deletes `INSTALLDIR` (and with it the provider profile). The file loads above `appsettings*.json` and below environment variables; `SettingsFile` in config can redirect it (absolute or relative to the content root). On first start it is seeded from the `SmsSettings` section of the install folder's `appsettings.json` and never overwritten afterwards. The `config` folder is SYSTEM and Administrators only (MSI, `install_service.bat`, or the service itself when it creates the folder), because it holds provider secrets.
- **Secrets.** All settings writes go through `SettingsStore` (merge, not replace; backups in `settings-backups/` next to the settings file). Secret values reach the browser only as `***`; posting `***` back keeps the stored value. The SOAP workbench sends `{secret:Key}` tokens that the server resolves just before the call.

## Startup and dependency wiring

`Program.cs` is the composition root. It:

- changes the current directory to the executable directory for Windows Service compatibility;
- loads `appsettings.json`, the environment-specific settings file, and environment variables;
- configures Serilog and Windows Event Log integration;
- registers Razor Pages, controllers, EF Core, HTTP clients, application services, mock/debug logs, the hosted SMS service, and health checks;
- applies EF migrations and runs seed initialization at startup;
- maps static assets, Razor Pages, API controllers, and `/health`.

Migration failure stops startup in Development but is logged and tolerated in Production. There is a bootstrap shim for databases created before EF migration history was introduced.

## Data model

`SCADADbContext` exposes these main sets:

- `Users`: operators and their phone/SMS/holiday preferences.
- `Groups`: notification groups.
- `GroupMembers`: many-to-many user/group membership.
- `SmsAudits`: immutable-ish per-recipient delivery history; user deletion is restricted to preserve audits.
- `DateDimensions`: calendar and Jewish/sabbatical holiday flags.
- `AlarmActions`: mapping to the WinCC OA `AlarmConditions` schema.
- `DBListBlocks`: WinCC OA block-name lookup data.
- `AlarmActionAudits`: local audit history for alarm-group mapping changes.

Database table/column names are explicitly mapped and include legacy/SCADA-prefixed naming. Do not infer physical names solely from C# entity names; check `SCADADbContext.cs` and the latest migration.

- `/` — dashboard and recent activity
- `/Users` — users and SMS/holiday toggles
- `/Groups` — groups and member assignment
- `/Alarms/ManageGroups` — alarm-to-group mapping
- `/Audit` — searchable delivery history and cleanup
- `/Calendar` — holiday calendar
- `/Settings` — provider/runtime settings and connectivity checks

This is a Razor Pages application, not MVC views or Blazor. Page behavior normally lives in a paired `.cshtml`/`.cshtml.cs` file and calls an injected service rather than using the DbContext directly.

## Configuration

Configuration is spread across `appsettings.json` and environment-specific overrides:

- `ConnectionStrings:DefaultConnection`
- `SmsSettings` (provider type, endpoint, HTTP method/content type, REST parameters/headers, SOAP envelope/body/placeholders/auth, credentials, sender, rate limits, duplicate window, retries, timeouts, test mode, XML logging)
- `Logging` and `Serilog`
- `Security`, `HealthChecks`, `BackgroundService`, `Maintenance`, and `Performance`

`SmsSettings` is monitored with `IOptionsMonitor`, so the Settings UI can update provider behavior without restarting. Dynamic values include message, group ID, alarm ID, priority, value, phone, TZ, first/last name, credentials, and sender identity. Phone is resolved per recipient; it is not part of the incoming SCADA payload.

Treat all `appsettings*.json` files as potentially sensitive. Never paste connection strings or provider credentials into documentation, tests, logs, commits, or issue reports. Use environment overrides or local configuration for secrets.

From the repository root:

```bash
dotnet restore
dotnet build --configuration Release
dotnet run
```

The normal Windows service/UI deployment expects `http://localhost:5000`. Playwright is configured for `http://localhost:5042`, so start the application on that URL before running browser tests, for example:

```powershell
$env:ASPNETCORE_URLS = "http://localhost:5042"
dotnet run
npm install

```

EF migrations should be created from the web project. `Data/SCADADbContextFactory.cs` supplies design-time context creation; inspect its selected configuration before running migration commands.

## Working conventions

- Follow existing Razor Pages and service-layer patterns.
- Inject services through constructors and keep database operations asynchronous.
- Put business logic in `Services/`, not page models or controllers.
- Preserve legacy API routes and the SCADA batch-script contract unless a migration is explicitly planned.
- Preserve existing database/table compatibility and audit history.
- Use Bootstrap 5.3 conventions already present in the UI.
- Log operational context, but mask phone numbers and never log secrets.
- Keep REST and SOAP provider modes, test mode, and live `IOptionsMonitor` reload behavior working when changing SMS settings.
- Add focused regression coverage. There is currently no dedicated C# unit-test project; CI primarily builds the application, while Playwright covers browser behavior.

## Repository state at context creation

The working tree already contains uncommitted Settings/Test UI changes, Playwright tests and reports, screenshots, and local tool settings. These are pre-existing user changes; inspect `git status` before editing and do not overwrite or clean them. Generated folders such as `bin/`, `obj/`, `node_modules/`, `playwright-report/`, `test-results/`, deployment packages, logs, screenshots, MSI files, and ZIP files are not source-of-truth code.

## Known operational caveats

- The application is Windows-first: SQL Server/LocalDB, Windows Service support, batch scripts, and WiX packaging are central to deployment.
- Startup sets the working directory from `Environment.ProcessPath`; assumptions based on the shell's launch directory may be wrong.
- Production startup continues after migration errors, so a running process does not prove the schema is current; check logs and health explicitly.
- Provider configuration supports several formats and live updates. Changes to payload resolution should be checked in REST, SOAP, and mock/test modes.
- Debug pages and mock endpoints expose operational detail. Mock endpoints require `SmsSettings:TestMode`; review exposure before enabling test/debug functionality outside a trusted network.
- README status claims may lag active code. Treat implementation, migrations, configuration models, and tests as authoritative when they disagree with prose.
